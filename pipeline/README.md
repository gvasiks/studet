# pipeline

Конвейер сбора каталога: обходит сайты вузов и пишет черновики программ
в тот же Postgres, что использует Next.js — сервисным ключом, напрямую,
без HTTP-API между Python и Next.js (CLAUDE.md, правило 3).

## Важно: что конвейер не делает

Он никогда не проставляет `verified_at`/`verified_by` — эти поля видит
только человек через Supabase Studio (CLAUDE.md, правило 6). Всё, что
сюда попало, помечено как «извлечено автоматически» и требует сверки
перед тем как доверять ему при принятии решения о поступлении.
Повторный запуск не затирает уже подтверждённые вручную записи — поля,
которых сборщик не нашёл, остаются такими, какими лежат в базе. Само собой
это не получается: программы вуза пишутся одной пачкой, и поле, которого
нет в одной строке, но есть в другой, PostgREST записал бы пустым. Поэтому
перед записью `catalog_diff.fill_missing_keys` дописывает недостающие поля
значениями из базы (исправлено 2026-10-04; до этого сбор стирал, например,
срок аккредитации, дописанный другим скриптом).

## Локальный запуск

```
py -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
./.venv/Scripts/python.exe -m playwright install chromium
```

Скопируйте `.env.example` в `.env` и заполните `SUPABASE_URL` /
`SUPABASE_SERVICE_ROLE_KEY` (Settings → API → service_role secret —
не anon, этот ключ обходит RLS).

```
./.venv/Scripts/python.exe src/main.py
```

**Сбои при сборе.** Один упавший источник не останавливает остальные —
ни когда не ответил сайт вуза, ни когда не ответила база. Запросы к
Supabase идут через `db_retry.execute`: временная ошибка (ответ 5xx,
обрыв связи) повторяется до трёх раз с паузами 5 и 15 секунд. В конце
прогона печатается список сбоев, код завершения ненулевой. Проверка без
сети и базы:

```
./.venv/Scripts/python.exe src/db_retry.py --selftest
./.venv/Scripts/python.exe src/main_selftest.py
```

## Расписание

`.github/workflows/scrape-catalog.yml` — по понедельникам в 01:00 UTC
(ночь по Риге), плюс запуск вручную. Нужно добавить в GitHub secrets
репозитория (Settings → Secrets → Actions) те же `SUPABASE_URL` и
`SUPABASE_SERVICE_ROLE_KEY` — сделать самостоятельно, сервисный ключ через
чат передавать не стоит второй раз. Плюс **переменную** (не секрет)
`SCRAPER_CONTACT` — публичный контакт для User-Agent. Выбран 2026-10-09:
`studypickeu@gmail.com`. Он записан в `pipeline/.env` и, со слов владельца
(2026-10-09), в переменных репозитория на GitHub (Settings → Secrets and
variables → Actions → вкладка Variables). Проверить просто: в журнале
любого прогона сборщика не должно быть строки «SCRAPER_CONTACT не задан».

## Диплом и описание программы (NIID)

`python src/enrich_niid_details.py` открывает страницу каждой программы в
NIID.lv и берёт то, чего нет в списках: степень (`Grāds`), профессиональную
квалификацию, название документа об образовании, начало описания и срок
аккредитации. Без `--apply` только показывает, что было бы записано.

- Берутся программы, для которых известна страница в NIID. У 286 программ
  она известна сразу — они из NIID и собраны. Для программ с сайтов вузов
  её находит `python src/match_niid_by_name.py` — по латышскому названию и
  уровню, строго: если в NIID у вуза на этом уровне не ровно одна программа
  с таким названием, программа пропускается и попадает в отчёт. Так
  заполняются РТУ, RAI, Ventspils, LNAA, Lutera и EKrA (200 из 209 программ
  на 2026-10-04; оставшихся 9 в NIID нет). Три уточнения правила описаны в
  шапке скрипта: тип NIID «код 44» считается бакалавриатом; у РТУ
  одноимённые программы различает вторая буква кода (`RTU_TYPE_CODES`);
  шесть программ привязаны вручную (`MANUAL_PAGES`). Отчёт печатает каждую
  найденную пару «программа -> страница NIID» — просмотрите его до `--apply`. У программ с английским названием (ЛУ и другие) страницы
  NIID нет — для них нужен другой способ.
- **ЛУ** — отдельный скрипт `python src/enrich_lu_details.py`: степень
  (`Obtainable degree or qualification`) и начало описания берутся с
  английской страницы программы на lu.lv и пишутся в `degree_awarded_en`
  и `description_en`. Те же флаги: без `--apply` — только показать,
  `--limit N`, `--all`, `--selftest`.
- **13 вузов с английскими страницами программ** (RSU, LMA, TSI, EKA, BSA,
  DU, LKA, LBTU, RGSL, RISEBA, RNU, Turība, SSE Riga) —
  `python src/enrich_site_details.py`: степень и начало описания с сайтов
  самих вузов; срок аккредитации — там, где он назван на странице (он
  пишется, только когда найден). JVLMA сюда не входит: на её сайте нет
  страниц программ со степенью и описанием. У каждого
  сайта свой разборщик текста (словарь `PARSERS`); новый вуз добавляется
  функцией и примером в `--selftest`. Можно назвать вуз: `… rsu --limit 5`.
  **LMA заполняется только локально** (сайт не отвечает серверу GitHub):
  `./.venv/Scripts/python.exe src/enrich_site_details.py --local --apply`.
  Достаточно раз в несколько месяцев — описания специализаций меняются
  редко; напоминания об этом нет.
- **Перед записью — сухой прогон и просмотр ВСЕГО лога**, а не первых
  строк. При первом запуске и у ЛУ, и у LMA в описание попадал посторонний
  текст (строка об аккредитации, меню сайта), и видно это было только по
  полному списку.
- Пауза между страницами — 10 секунд (robots.txt сайта): полный обход —
  40 минут одного ожидания плюс загрузка страниц (замер 2026-10-03). Скрипт пропускает страницы, прочитанные меньше 30
  дней назад, поэтому прерванный запуск можно просто повторить.
- По расписанию — раз в месяц: `.github/workflows/enrich-niid.yml`.
- Описание сохраняется началом (до 600 знаков), а не целиком: это
  авторский текст вуза; на карточке рядом стоит ссылка на полный текст.
- Подтверждения человеком эти поля не требуют (не правило 6); на карточке
  они показываются с пометкой об автоматическом извлечении.

## Локальный сбор (РТУ и LMA)

Сайты `rtu.lv` и `lma.lv` не отдают страницы с программами серверу GitHub
(проверено 2026-10-03: на GitHub сборщики каталога РТУ и LMA нашли 0
программ, с компьютера в Риге в тот же день — 164 и 35). Третий источник
того же сайта, `rtu_liepaja`, на GitHub «сработал», но записал в каталог
название «www.rtu.lv» у всех трёх своих программ — сайт отдал серверу
страницу с другим заголовком. Поэтому расписание GitHub пропускает все три
источника (`main.py --skip-local`), а собираются они **раз в неделю на
компьютере владельца**:

```
./.venv/Scripts/python.exe src/main.py --local
```

Занимает около пяти минут. Список таких источников — в одном месте:
`src/scrape_scope.py`. Правило: туда идут ВСЕ источники сайта, который не
отвечает серверу GitHub, а не только те, что вернули ноль программ.

От повторения случая с «www.rtu.lv» защищает и сам `main.py`: источник, у
которого название хотя бы одной программы — адрес сайта или пусто, не
записывается целиком и попадает в ошибки прогона.

**Чтобы не забыть** — `.github/workflows/local-scrape-reminder.yml`: раз в
день проверяет, когда эти источники обновлялись в последний раз
(`src/check_local_sources.py`), и падает, если прошло больше 7 дней. GitHub
присылает письмо с темой «Reminder: run local scrape (RTU, LMA)»; письма
приходят каждый день, пока сбор не запущен. В логе упавшей проверки —
готовая команда.

Если письма не приходят, проверьте в настройках своего аккаунта GitHub
(Settings → Notifications, раздел про Actions), что уведомления о прогонах
workflow включены для Email. Письма о запланированных workflow GitHub
шлёт тому, кто последним менял расписание в файле workflow.

## Литва (`lt_lamabpo`)

Литовский каталог собирает один сборщик — `src/sources/lt_lamabpo.py`. Он
читает файл программ официального калькулятора LAMA BPO (общий приём, 28
учреждений) и карточки государственного реестра AIKOS: уровень, язык,
степень, срок и описание программы; у учреждения — государственное оно или
нет, английское название и сайт.

```
python src/sources/lt_lamabpo.py --selftest   # разбор на встроенных примерах, без сети
python src/sources/lt_lamabpo.py              # собрать и напечатать сводку, без записи в базу
python src/main.py lt_lamabpo                 # собрать и записать в базу
```

- **Запускается только по имени.** В `main.py` он стоит в `BY_NAME_ONLY`:
  `python src/main.py` без аргументов и недельное расписание GitHub его не
  трогают — так остаётся и после запуска Литвы. Обычный способ обновить
  литовские данные — `python src/lt_refresh.py` (раздел «Литва: сбор и
  сторож» ниже).
- **Идёт около часа:** примерно 700 страниц реестра с паузами. С
  `SCRAPE_CACHE=1` страницы сохраняются на сутки, повторный запуск в тот же
  день занимает минуты.
- **Литовские факты не ждут подтверждения человеком** и показываются с
  пометкой «извлечено автоматически» — решение владельца 2026-10-05, только
  для Литвы. `verified_at` у них пустой, в очередь проверки они не попадают.
- **Чего сборщик не пишет:** цены, числа бюджетных мест и типа
  финансирования (источники их не сообщают), магистратуры и докторантуры
  (их нет в общем приёме).
- **Пороги** — `MIN_PROGRAMME_COUNT` в `main.py`, по одному на учреждение
  (снимок 2026-10-05). Список общего приёма меняется раз в год; после
  обновления пороги пересматриваются вручную.
- **Код учреждения** — его сокращение; если оно занято латвийским, добавляется
  `-lt` (`lka-lt`). Список занятых кодов — `TAKEN_SLUGS` в сборщике: при
  добавлении латвийского вуза его надо дописать туда.

### Формулы конкурсного балла (фаза 3)

В Литве правило расчёта одно на страну: около сорока «формул» (наборов из
четырёх составляющих с весами), и у каждой строки общего приёма стоит номер
своей. Источник — открытые файлы официального калькулятора LAMA BPO.

```
python src/lt_formulas.py --selftest                                    # разбор текста формул
python src/lt_formulas.py                                               # сводка по файлу с сайта
python src/lt_load_formulas.py --save-payload .cache/lt_formulas.json   # собрать и показать, без записи
python src/lt_load_formulas.py --payload .cache/lt_formulas.json --apply
```

- Загрузчик пишет таблицы `lt_formula`, `lt_formula_component` и
  `lt_admission_unit` (строки общего приёма, привязанные к программам
  каталога). Сначала должен пройти сбор каталога — привязка идёт по его кодам.
- **Отметку о сверке (`checked_at`) загрузчик не ставит.** Без неё формула
  посетителям не видна — так устроена политика доступа. Отметка появляется
  после сверки расчёта с официальным калькулятором; если состав формулы в
  файле изменился, загрузчик её снимает.
- У программы, строки которой идут по разным формулам (на 2026-10-06 таких
  три — предметная педагогика), расчёт не показывается.
- **Сверка с официальным калькулятором — ручная.** Сервис расчёта LAMA BPO
  запрещает автоматических клиентов (`robots.txt`), поэтому
  `lt_check_calculator.py` ему ничего не отправляет: он готовит 30 случаев с
  выдуманными оценками (`--save` → `docs/checks/lt-calculator-cases-2026.json`).
  Лист для ввода с нашими ответами собирает `node scripts/lt-check-sheet.mjs`;
  ответы вписывает человек, сравнивает тест `src/lib/lt-score-official.test.ts`.
- **Отметку о сверке ставит `lt_mark_checked.py`** — только при записи о
  сверке в файле случаев (блок `owner_check`, не меньше 13 совпавших
  случаев) и только формулам из школьных предметов. Формулы со
  вступительным экзаменом или спортивными достижениями он не отмечает: их
  расчёт не сверялся.
- Год приёма — константа `ADMISSION_YEAR` в загрузчике. Когда LAMA BPO
  выложит правила следующего года, её надо поменять; прошлогодние строки
  остаются в таблицах.

Направления литовских программ — отдельный загрузчик:

```
python src/lt_load_fields.py --selftest
python src/lt_load_fields.py            # сводка по группам, без записи
python src/lt_load_fields.py --apply
```

- Пишет таблицу `lt_programme_field`: группа и направление программы по
  классификатору общего приёма (17 групп, 102 направления). Источник — тот
  же открытый файл программ калькулятора; реестр заново не обходится.
- Запускать после `lt_load_formulas.py`: привязка идёт через строки приёма
  (`lt_admission_unit`). Строки без программы в базе показываются в сводке.
- По направлению работает фильтр «интересы» в литовском каталоге и анкете
  (`src/lib/lt-fields.ts`). Человек эту разметку не подтверждает: она взята
  из официального списка как есть.

Цифры прошлого приёма литовских программ:

```
python src/lt_load_admission_stats.py --selftest
python src/lt_load_admission_stats.py            # скачать, посчитать, показать сводку
python src/lt_load_admission_stats.py --apply
```

- Источник — открытый набор LAMA BPO на data.gov.lt (набор 2914): таблицы
  `Programa` и `Prasymas`. **`Prasymas` (76 МБ) читается потоком и не
  сохраняется**: в нём обезличенные, но построчные данные о людях. В базу
  (`lt_admission_stat`) идут только суммы по программе. Таблицу `Profilis`
  того же набора не скачивать.
- Считается основной приём последнего года, который есть в наборе. Набор
  обновляется раз в год — после обновления запустить заново.
- С каталогом суммы сходятся по государственному коду программы
  (`lt_admission_unit.state_code`) и городу. Код читает сборщик из карточки
  реестра, пишет `lt_load_formulas.py` — он должен пройти раньше. В сводке
  видно, сколько программ осталось без чисел и почему.
- В наборе программа одна на все формы и языки обучения в городе, поэтому
  строки каталога, различающиеся только формой или языком, получают одни и
  те же числа.
- Адрес набора содержит номер версии (`versions/729`). Если портал выпустит
  новую версию и старый адрес перестанет отдавать свежие данные — поправить
  константу `_RESOURCE` в загрузчике.

Что стало с выпускниками литовских направлений:

```
python src/lt_load_field_outcomes.py --selftest
python src/lt_load_field_outcomes.py            # разобрать файл, показать сводку
python src/lt_load_field_outcomes.py --apply
```

- Источник — PDF в `docs/sources/lt/dTkpkNxT2eM.pdf` (приложение к проекту
  постановления правительства Литвы, данные NŠA). **Сайт `lrv.lt` закрыт
  проверкой «вы не робот», скрипт файл не скачивает** — его сохраняет
  человек. Новый документ: положить файл, поправить `PDF_PATH`,
  `SOURCE_URL`, `PUBLISHED_ON`, годы выпуска и `EXPECTED_ROWS`.
- Пишет `lt_field_outcome`: показатели по направлению и ступени по всей
  стране. Разреза по вузам и программам в источнике нет.
- Строки с долей ровно 0 % или 100 % не загружаются — это очень маленькие
  группы, а числа выпускников в источнике нет. В сводке они перечислены.
- С каталогом строки сходятся по названию направления и уровню программы
  (`lt_programme_field` — должен быть заполнен). Явные пары разных
  написаний — словарь `ALIASES`; по смыслу названия не склеивать.
- Число строк в каждой таблице документа сверяется с `EXPECTED_ROWS`: если
  разбор что-то потерял, запись не идёт.

Разметка направлений (`seed_programme_fields.py`,
`confirm_programme_fields_by_rule.py`) работает только с латвийскими
программами.

## Литва: сбор и сторож

Литовские данные собираются отдельно от недельного латвийского сбора.

- **`.github/workflows/scrape-lithuania.yml`** — по расписанию: 3-го числа
  каждого месяца и по четвергам в июне–августе (сезон приёма); есть и кнопка
  «Run workflow». По порядку: каталог, строки приёма с формулами,
  направления, показатели выпускников.
- **Этот прогон падает часто, и это не авария.** Реестр программ
  `aikos.smm.lt` серверу GitHub отвечает ненадёжно. Пять прогонов 9–10
  октября 2026 года: два прошли, один упал на не ответившей странице, один —
  на тридцати неполных карточках из шестисот, один не уложился в два с
  половиной часа. Расписание оставлено по решению владельца (2026-10-10).
  Упавший прогон базу не портит: неполная карточка запрашивается заново (до
  трёх раз), после 30 повторов за обход сборщик останавливается сам, а
  проверка числа программ не даёт записать неполный каталог. Письмо об
  упавшем прогоне можно не трогать, если следующий прошёл.
- **Надёжный путь — с вашего компьютера**, одной командой в папке
  `pipeline`:

  ```
  .venv\Scripts\python.exe src\lt_refresh.py
  ```

  Она по порядку обновляет каталог, строки приёма с формулами и направления
  и останавливается на первом сбое; идёт около 35 минут. С ключом `--yearly`
  — ещё цифры прошлого приёма и показатели выпускников. Нужна, когда прогон
  на GitHub упал, а данные нужны сейчас, и когда написал сторож.
- **Цифры прошлого приёма в прогон на GitHub не входят**: портал
  `data.gov.lt` его серверу не отвечает вовсе. Они обновляются раз в год
  командой с ключом `--yearly` (календарь ниже, строка «сентябрь»).
- **`.github/workflows/lithuania-health.yml`** — ежедневный сторож
  (`check_lt_sources.py`): падает и присылает письмо, если каталог, строки
  приёма или направления не обновлялись дольше 45 дней — то есть не прошёл
  ни один прогон подряд. Тогда — команда выше.
- **Загрузчик формул сам останавливается в двух случаях** — прогон (или
  команда обновления) на этом прерывается, и это уже сигнал для человека:
  - код 2 — файл калькулятора рассчитан на другой год приёма, чем
    `ADMISSION_YEAR`. В базу ничего не пишется. Что делать — см. годовой
    календарь ниже, строка «декабрь–январь»;
  - код 3 — у формулы, сверенной с калькулятором, изменился состав. Отметка
    о сверке снята, расчёт балла по таким программам закрыт до новой ручной
    сверки (как сверять — выше, «Сверка с официальным калькулятором»).

## Литва: что обновлять в течение года

Источники обновляются раз в год, каждый в своё время. Обычное обновление
делает расписание (или команда `lt_refresh.py`); ниже — то, что сверх него.

| Когда | Что меняется | Что делать |
|---|---|---|
| до 1 декабря | Вузы объявляют принципы балла на следующий приём (закон о науке и образовании, ст. 59, ч. 4) | Пока ничего: ждать, когда LAMA BPO обновит файлы калькулятора |
| декабрь–январь | LAMA BPO обновляет калькулятор (порядок приёма 2026 года, п. 14: «в начале календарного года») | Загрузчик формул остановится с кодом 2. Поменять `ADMISSION_YEAR` в `lt_load_formulas.py`, собрать новые случаи (`lt_check_calculator.py --save`), сверить вручную не меньше 13 случаев с официальным калькулятором, записать сверку в файл случаев и запустить `lt_mark_checked.py`. До этого расчёт балла у Литвы закрыт |
| февраль–март | Министерство готовит проект постановления о местах за счёт государства; в приложении — показатели выпускников (в 2026 году датирован 19 февраля) | Сайт закрыт проверкой «вы не робот»: сохранить PDF руками в `docs/sources/lt/`, поправить константы в `lt_load_field_outcomes.py` (путь, адрес, дата, годы выпуска, число строк), запустить с `--apply` |
| до 15 апреля | LAMA BPO публикует список программ приёма (порядок 2026 года, п. 14) | Каталог обновит расписание; если прогон упал — `lt_refresh.py`. Если учреждений или программ стало заметно меньше, сбор упадёт на пороге — посмотреть глазами и поправить пороги в `main.py` |
| апрель | LAMA BPO утверждает порядок приёма на год (в 2026 году — 17 апреля) и даты приёма | Перечитать порядок и поправить словарь и права (`lt.json`, `en-lt.json`, `lv-lt.json`): номера пунктов и числа меняются. Внести даты приёма |
| июнь–август | Идёт приём; вузы могут снимать программы | Расписание переходит на еженедельный сбор само. Если прогон упал два четверга подряд — `lt_refresh.py`: сторож напомнит только через 45 дней, для сезона это поздно |

Чего ни расписание, ни команда обновления не заметят сами: новой версии
открытого набора, нового PDF о выпускниках и нового порядка приёма. Эти три
строки — только по календарю.

## Литва: если база потеряна

Всё литовское восстанавливается из источников и из репозитория — в базе нет
ничего, что существует только там:

1. Применить миграции из `supabase/migrations/` (в том числе
   `20261005…` – `20261008…`).
2. Запустить `python src/lt_refresh.py --yearly` (раздел «Литва: сбор и сторож»).
3. Вернуть отметку о сверке формул: `python src/lt_mark_checked.py`. Запись
   о вашей ручной сверке лежит в репозитории
   (`docs/checks/lt-calculator-cases-2026.json`, блок `owner_check`), скрипт
   читает её оттуда.

Полный дамп (`backup.yml`) снимает всю схему `public`, литовские таблицы в
него входят.

## Наблюдение за конвейером и резервные копии

План 2026-09-21, неделя 1, пункты 08 и 06.

- Каждый прогон `main.py` (полный — без аргументов или с `--skip-local`) пишет строку в
  `pipeline_run`: начало, конец, статус, число источников и программ,
  первые ошибки. `.github/workflows/pipeline-health.yml` — отдельный
  ежедневный сторож: падает (и присылает письмо через уведомления GitHub
  о сломанном запланированном workflow), если последнего УСПЕШНОГО
  ПОЛНОГО сбора не было больше 9 дней. Точечные перезапуски одного
  источника (`python src/main.py rsu`) в этот счёт не идут — иначе починка
  одного вуза маскировала бы остановившееся расписание. Дата последнего
  успешного сбора видна на `/verification`.
- `.github/workflows/backup.yml` (по понедельникам, через два часа после
  сбора) кладёт снимок подтверждённых фактов в `docs/backups/` (коммитится
  в репозиторий, см. `docs/backups/README.md`) и полный дамп схемы `public`
  в артефакт прогона (`pg_dump`, нужен секрет `SUPABASE_DB_URL` — строка
  подключения Postgres из дэшборда Supabase, Settings → Database →
  Connection string; без него снимок подтверждений всё равно идёт, дамп —
  нет).
- `python src/restore_verified.py` накатывает снимок `docs/backups/
  verified-facts.json` обратно на базу — по устойчивым слагам, не по
  UUID. Без `--apply` — сухой прогон: только проверяет, что каждый слаг
  из снимка ещё находится в текущем каталоге (ловит расхождение, если
  программа исчезла или переслагована при повторном сборе), ничего не
  пишет. С `--apply` пишет verified_at/verified_by ИЗ снимка — это
  восстановление уже принятого человеком факта, не новое подтверждение.
  Критерий пункта 06 («снимок восстанавливает подтверждения на пустой
  базе», раз в квартал) в этом окружении не проверить целиком — нужен
  отдельный одноразовый Supabase-проект или локальный `supabase start`
  (Docker), ни того ни другого здесь нет; сухой прогон по живой базе —
  ближайшая проверка, которая доступна без них.

## Годовой цикл сверки

Компаньон к пункту 08 плана (декабрьское обновление формул на новый учебный
год): `python src/formula_year_diff.py` сравнивает коэффициенты старой
(закрытой через `valid_to`) и новой формулы для каждой программы, у которой
есть обе, и явно кричит («ПОДОЗРИТЕЛЬНО»), если вес слагаемого изменился
больше чем втрое в любую сторону, или слагаемое целиком появилось/пропало.
Не подтверждение и не проверка на правильность — только сигнал «посмотри
сюда внимательнее» перед тем, как подтверждать через Studio, специально
для декабря, когда меньше всего времени на построчную сверку.

**Данные о выпускниках — тоже раз в год.** Блок «Что стало с выпускниками»
показывает самый свежий выпуск, только если он не старше 5 лет
(`MAX_COHORT_AGE_YEARS` в `src/lib/outcomes.ts`). Сейчас самый свежий выпуск
в датасете — 2023 год, поэтому без обновления блок исчезнет со всех карточек
в 2029 году. В декабре проверьте, вышла ли на data.gov.lv новая редакция
датасета мониторинга выпускников, и перезагрузите её
(`python src/import_graduate_outcomes.py`, см. справку в начале файла).

## Вежливый обход

Все сборщики ходят через `src/polite.py`, подключённый в `main.py`:
честный User-Agent `StudyPickBot/1.0 (+контакт)`, пауза не меньше 1,5 с между
страницами одного домена (у niid.lv по `robots.txt` — 10 с), запрещённые
`robots.txt` адреса не открываются, картинки и шрифты не грузятся. После
каждого источника в журнале строка `polite: …` с числами. Для отладки
сборщика локально включите `SCRAPE_CACHE=1` — повторные запуски пойдут из
кэша `pipeline/.cache/` без обращений к сайту. Переменные — в `.env.example`.

## Источники

Каждый вуз — свой модуль в `src/sources/`, с функцией `scrape() ->
(UniversityDraft, list[ProgrammeDraft])`. Структура страниц у вузов
разная, общего парсера не будет — см. `src/sources/turiba.py` как
образец: селекторы найдены и проверены вручную в браузере, не угаданы.

Сейчас источников — один (Turība, английский раздел, 17 программ).
Следующий вуз добавляется отдельным файлом + строкой в `SOURCES`
в `src/main.py`.

## Сознательно не собираем пока

- **Стоимость** — у Турибы это одна общая таблица на всех, не привязанная
  к конкретной программе URL-ом; парсить текстовую таблицу вслепую
  ненадёжнее, чем внести цифры руками в Studio.
- **Дедлайн подачи** — не нашёлся в структурированном виде per-programme.
- **Латышское название программы** — конвейер читает английский раздел
  сайта; `name_lv` для этих программ пока пустой, заполняется вручную.

Все три поля и так по правилу 6 подтверждает только человек — конвейер
не обязан их доставать, чтобы каталог был полезен.
