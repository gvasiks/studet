## Находки

### 1. Средняя — полный дамп базы в артефакте публичного репозитория (A01, A02)

**Что.** Задача `full-dump` в `.github/workflows/backup.yml` снимает `pg_dump` всей схемы
`public` и выкладывает его артефактом прогона на 14 дней. Репозиторий `gvasiks/studet`
публичный (проверено через `api.github.com`: `"visibility": "public"`), а артефакт
публичного репозитория скачивает **любой вошедший пользователь GitHub**. В дампе есть всё,
что закрыто от публичного ключа: `verified_by`, `disputed_reason`, `source_copy_*`,
таблица `pipeline_run`, а также неподтверждённые черновики (правило 6) и строки скрытых
программ. Срок 14 дней (решение 2026-10-10) уменьшает окно, но не закрывает доступ.

**Почему сейчас безопасно.** Дамп ещё ни разу не снялся: с 5 октября каждый прогон падал
(прямое подключение Supabase — только IPv6). Причина уже найдена в коммите `0f5a536`
(сегодня): нужен адрес Session pooler в секрете `SUPABASE_DB_URL`. **Как только владелец
поменяет секрет, следующий понедельничный прогон выложит дамп в открытый доступ.**
Эту часть (`pg_dump`) я не дублирую — только шифрование.

**Воспроизведение.** После первого успешного прогона: войти на GitHub под любым
посторонним аккаунтом → `github.com/gvasiks/studet/actions/workflows/backup.yml` →
прогон → Artifacts → `studet-db-dump-…` скачивается. Список артефактов виден и без входа:
`curl https://api.github.com/repos/gvasiks/studet/actions/artifacts` (сейчас
`total_count: 0`).

**Исправление (предлагаю).** Шифровать дамп перед выкладкой. `gpg` уже стоит на
серверах GitHub — новой зависимости нет:

```yaml
      - name: Зашифровать дамп
        env:
          BACKUP_PASSPHRASE: ${{ secrets.BACKUP_PASSPHRASE }}
        run: |
          test -n "$BACKUP_PASSPHRASE" || { echo "::error::нет BACKUP_PASSPHRASE"; exit 1; }
          gpg --batch --yes --pinentry-mode loopback --passphrase-fd 0 \
              --symmetric --cipher-algo AES256 \
              --output studet-public-schema.dump.gpg studet-public-schema.dump \
              <<< "$BACKUP_PASSPHRASE"
          rm studet-public-schema.dump
```

**Исправлено в коде 2026-11-16** («Да, шифруй дамп»): шаги «Проверить наличие секрета
BACKUP_PASSPHRASE» (до дампа) и «Зашифровать дамп» в `backup.yml`, наружу уходит только
`.gpg`; расшифровка — `docs/backups/README.md`, «Полный дамп». Действует после пуша и
после того, как владелец заведёт секрет. Пока секрета нет, задача `full-dump` падает
с понятной ошибкой и ничего не выкладывает.

и выкладывать `studet-public-schema.dump.gpg`. Владельцу: придумать длинную фразу,
сохранить её в менеджер паролей и в секрет `BACKUP_PASSPHRASE` **до** замены
`SUPABASE_DB_URL`. Восстановление: `gpg -d studet-public-schema.dump.gpg > dump` и
`pg_restore`. Чем жертвуем: без фразы копию не развернуть — потеря фразы равна потере
копии. Альтернатива проще, но хуже — не выкладывать дамп вовсе (тогда полной копии нет).

### 2. Низкая — CSP не ограничивает скрипты (A02, A05)

**Что.** Политика запрещает фреймы, плагины и чужие формы, но не задаёт `default-src` и
`script-src`: если когда-нибудь появится XSS, браузер выполнит и встроенный, и чужой
скрипт. Решение 2026-10-16 было осознанным (строгая политика в Next.js требует nonce на
каждый ответ и убирает статическую отдачу). Сейчас поверхность XSS очень мала (см. «в
порядке»), поэтому важность низкая.

**Воспроизведение.** `curl -sI http://localhost:3000/lv | grep -i content-security` после
`npm run build && npm start` — в политике нет `script-src`.

**Исправление (предлагаю, без nonce).** Добавить ограничение источников без запрета
встроенных скриптов — статическая отдача остаётся:
`default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self'; connect-src 'self' <адрес Supabase>
https://eu.i.posthog.com` плюс уже имеющиеся директивы. Это не спасает от встроенного
скрипта, но запрещает загрузку чужого файла и отправку данных на чужой адрес.
Сначала — как `Content-Security-Policy-Report-Only` на неделю, проверка e2e-тестами на
ошибки в консоли, потом — включить. Чем рискуем: забытый источник (например, картинка
с чужого домена) перестанет грузиться.

### 3. Низкая — actions закреплены тегом, нет Dependabot (A03, A08)

**Что.** Все 10 workflow используют `actions/checkout@v4`, `actions/setup-python@v5`,
`actions/setup-node@v4`, `actions/upload-artifact@v4`. Тег можно перевесить; хеш — нет.
Все actions — собственные GitHub (`actions/*`), сторонних нет, поэтому риск низкий.
Файла `.github/dependabot.yml` нет — новые версии actions и пакетов никто не предлагает.

**Воспроизведение.** `grep -h "uses:" .github/workflows/*.yml | sort -u`.

**Исправление.** Заменить теги на хеши с комментарием версии
(`actions/checkout@<40 знаков> # v4.x.y`) и добавить `.github/dependabot.yml` на
`github-actions` (раз в месяц) — Dependabot встроен в GitHub, зависимости проекту не
добавляет. Он же будет обновлять хеши. Чем платим: раз в месяц PR на обновление, которые
надо смотреть и сливать.

### 4. Низкая — `npm audit` (A03)

**Что.** `npm audit --omit=dev`: 53 низких, все — одна причина: `deepmerge`
(GHSA-gcqx-w48m-w2h4, «загрязнение прототипа») внутри `@heroui/theme` v2. Исправленной
версии HeroUI v2 нет; переход на v3 запрещён правилами проекта. `deepmerge` сливает
объекты темы, заданные в коде, а не ввод посетителя — путь атаки не виден. В
инструментах разработки ещё 7 умеренных: `minimatch` внутри `typescript-eslint` (отказ в
обслуживании на злонамеренном шаблоне; шаблоны — наши), в сайт не попадает.

**Воспроизведение.** `npm audit --omit=dev` и `npm audit`.

**Исправление.** Принять риск, следить: еженедельная проверка (ниже) падает на `moderate`
и выше в зависимостях сайта — сегодняшнее состояние она пропускает, новое — нет.

### 5. Низкая — ссылки из базы без проверки схемы (A05)

**Что.** Около 25 мест выводят адрес из базы прямо в `href` (`source_url`, ссылка «где
подать», SAIS и т. д.: `programmes/[university]/[programme]/page.tsx:370–624`,
`ForeignDocuments.tsx:164`, `VuppAdmissionStats.tsx:141` и др.). Проверка схемы в базе
есть только у `ee_admission.sais_url`. Писать в базу может только сервисный ключ, а
React 19.3.1 сам блокирует `javascript:`-адреса, поэтому сейчас эксплуатировать нечем.
Риск — на будущее: адрес, взятый сборщиком со страницы вуза, при смене версии React или
при выводе не через JSX.

**Воспроизведение.** Только мысленно: строка `source_url = 'javascript:alert(1)'`,
записанная сервисным ключом, попала бы в `href` без проверки. Опыт на живой базе не
ставился — он требует записи.

**Исправление.** Одна функция на пять строк в `src/lib/` — `safeHref(url)`: вернуть адрес,
только если он начинается с `https://` или `http://`, иначе `undefined` (ссылка не
рисуется), и пропустить через неё все такие места. Либо (или вместе) `check (source_url
~ '^https?://')` миграцией на таблицах фактов — но это владелец применяет вручную, а
существующие строки надо сначала проверить.

### 6. Низкая — служба systemd ограничена не полностью (A02)

**Что.** `deploy/studypick.service`: `ProtectSystem=full` (а не `strict`), пользователь
сайта владеет папкой с кодом — взломанный процесс может переписать свой код, и это
переживёт перезапуск. Нет `PrivateDevices`, `ProtectKernel*`, `RestrictAddressFamilies`,
`CapabilityBoundingSet=`.

**Воспроизведение.** На сервере: `systemd-analyze security studypick` — оценка «exposure».

**Исправление.** Добавить в `[Service]`:
`ProtectSystem=strict`, `ReadWritePaths=/srv/studypick/app/.next`, `PrivateDevices=true`,
`ProtectKernelTunables=true`, `ProtectKernelModules=true`, `ProtectControlGroups=true`,
`RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `CapabilityBoundingSet=`,
`LockPersonality=true`, `RestrictNamespaces=true`. **Не** добавлять
`MemoryDenyWriteExecute` — ломает JIT Node.js. Проверить на сервере, что сайт
стартует и пишет кэш `.next/cache`. Разделение «код принадлежит root, служба только
читает» сильнее, но меняет `update.sh` — предлагаю позже.

### 7. Замечание — `pipeline_health` с правами владельца (A01)

View `pipeline_health` (`20260922090000_pipeline_run.sql`) создана без
`security_invoker`, поэтому читает `pipeline_run` в обход RLS. Это сделано намеренно:
публичному ключу видны только четыре поля сводки (время последнего успеха, статус, время,
число ошибок), сама таблица отдаёт `[]`. Утечки нет. Встроенный советник безопасности
Supabase (Advisors → Security) пометит её как `security_definer_view` — это ожидаемо.

### 8. Замечание — при закрытом сайте HSTS не отправляется (A02)

Пока включён пароль, на все запросы отвечает Caddy (401) без заголовков сайта, поэтому
браузер не запоминает HSTS. Опасности мало: `http` всё равно переадресуется на `https`.
Можно добавить в блок `studypick.eu` Caddyfile `header Strict-Transport-Security
"max-age=31536000"` — тогда заголовок будет и на 401. После открытия сайта заголовки
проверить снаружи: `curl -sI https://studypick.eu/lv`.

### 9. Замечание — настройки GitHub не проверены (A07, A08)

Без входа не видно: включена ли двухфакторная защита аккаунта, secret scanning и push
protection (для публичных репозиториев GitHub включает их по умолчанию). От аккаунта
зависят и сайт (`git pull` в `update.sh`), и все секреты Actions. Владельцу —
проверить в Settings → Password and authentication и в Settings → Code security
репозитория.

## Еженедельная автоматическая проверка (предложение)

### Вариант А (рекомендую) — workflow GitHub Actions по расписанию

`.github/workflows/security-weekly.yml`, раз в неделю (например, вторник 05:00 UTC), с
`permissions: contents: read` и actions на хешах. Падает при любой находке — GitHub
присылает письмо, как у остальных сторожей. Шаги:

1. `npm ci` и `npm audit --omit=dev --audit-level=moderate` — сегодняшние низкие
   (`deepmerge`) пропускает, новое — нет.
2. OSV для Python: `pip install --dry-run --report` по `pipeline/requirements.txt` и
   запрос к `api.osv.dev/v1/querybatch` — скрипт на ~20 строк, без `osv-scanner` и
   сторонних actions.
3. RLS публичным ключом: `scripts/check-rls.mjs` (~60 строк). Список таблиц берёт **из
   миграций**, поэтому новая таблица попадает в проверку сама. По каждой: `insert`,
   `update`, `delete` с пустым условием → ждём `42501`; служебные колонки → `42501`;
   `verification_queue` закрыта; регистрация в Auth выключена. Секреты те же, что у
   `ci.yml` (`NEXT_PUBLIC_SUPABASE_*`), сервисный ключ не нужен.
