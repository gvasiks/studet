# Список измерений до аналитики (план 2026-09-21, пункт 10, черновик)

PostHog ещё не подключён (пункт Д3, неделя 14) — это план на подключение,
не описание того, что уже работает. Документ существует, чтобы решить
ЗАРАНЕЕ, какие события нужны и что они должны означать, а не придумывать
их на ходу при интеграции (тогда легко случайно собрать больше, чем
обещано в политике).

**Каждое событие ниже сверено с `docs/PRIVACY-CHECKLIST.md` (раздел 2,
строка «Аналитика»)** — те ограничения обязательны, не пожелание:
PostHog, серверы ЕС, без cookies, без хранения в браузере
(`persistence: "memory"`), без автосбора полей ввода, без записи сессий,
IP не хранится, экзамены не попадают. `persistence: "memory"` не значит
«воронка невозможна» — Next.js App Router переходит между страницами на
клиенте без перезагрузки, и данные в памяти переживают такой переход;
рвётся только на закрытии вкладки/обновлении страницы. Это ограничение
воронки, а не блокер: она видит путь ВНУТРИ одного визита, не между
визитами через недели.

## Главный вопрос: какой вход приводит к расчёту балла

Три пути к калькулятору/подбору:
1. **Анкета** → результаты → карточка программы → калькулятор.
2. **Поиск по каталогу** (`/programmes`, фильтры) → карточка → калькулятор.
3. **Прямой переход из выдачи** — сразу на `/programmes/[вуз]/[программа]`
   (SEO), минуя и анкету, и каталог.

| Вопрос | Как отвечаем | Порог «да» (черновик — решает владелец) |
|---|---|---|
| Через анкету реально доходят до расчёта? | Воронка PostHog по путям `$pageview`: `/survey` → `/programmes/*/*` → `/programmes/*/*/calculator` (без единого доп. события — путь виден по обычным `$pageview`) | ≥15% дошедших до конца анкеты открывают калькулятор в той же сессии |
| Через каталог реально доходят? | Та же воронка от `/programmes` (без предварительного `/survey` в сессии) | ≥5% посетителей `/programmes` открывают хоть один калькулятор |
| Прямые SEO-переходы доходят? | Сессии, где первая страница — `/programmes/[вуз]/[программа]` (не `/`, не `/survey`, не `/programmes`), далее — открыт ли калькулятор той же программы | ≥10% таких сессий открывают калькулятор |
| Что из трёх — главный источник расчётов? | Доля каждого пути среди ВСЕХ сессий, дошедших до калькулятора | Нет числового порога — просто сравнение долей раз в месяц после запуска |

Если ни один порог не набирается за первый месяц с реальным трафиком —
это сигнал разбираться, а не сразу менять продукт (мало данных = шумно).

## Дополнительные вопросы

| Вопрос | Событие | Свойства (без личных данных) | Порог «да» |
|---|---|---|---|
| Долистывают ли анкету до конца? | `survey_completed` — на шаге `submit` (см. `survey.submit` = «See programmes») | нет (сам факт события — уже ответ) | ≥60% начавших анкету доходят до конца |
| Калькулятор реально считает балл, а не просто открывается? | `calculator_result_shown` — когда посчитанный балл отрисовался на экране | `university_slug`, `programme_slug` (какая программа — не кто её считал) | ≥30% открывших калькулятор доводят до результата (ввели минимум нужных предметов) |
| То же для обратного поиска (`/match`) | `match_result_shown` — когда список программ с посчитанным баллом непустой | нет (или количество найденных программ — агрегат, не факт о человеке) | ≥30% дошедших до `/match` с непустым списком |
| Страницы читают, грузятся быстро? | Core Web Vitals (LCP/INP/CLS) — встроенный сбор PostHog, не отдельное событие | автоматически, PostHog сам не хранит содержимое полей | LCP < 2.5s, INP < 200ms, CLS < 0.1 на p75 (CLAUDE.md, раздел «Работоспособность») — критерий уже есть в проекте, здесь просто подключаем измерение к нему |

**Явно НЕ считается «дополнительным вопросом» и не измеряется:** какие
именно экзамены/предметы/проценты ввёл человек, какие фильтры анкеты он
выбрал по отдельности (сами по себе, не в составе пути), что он ищет в
поиске каталога текстом. Не потому что технически сложно — потому что
это прямая дорога к «а давайте посмотрим, что чаще всего ищут
16-летние» — ровно то, что CLAUDE.md запрещает («экзамены, оценки, всё,
по чему узнаётся школьник»).

## Что НЕ собираем (граница, не список примеров)

- Значения полей ввода: результаты CE, проценты, оценки аттестата — ни в
  событии, ни в свойствах, ни как часть URL, который PostHog мог бы
  захватить автосбором (автосбор полей выключен настройкой, но URL всё
  равно стоит явно очищать перед отправкой, если в нём когда-нибудь
  появятся такие параметры — сейчас их там нет, анкета не кладёт экзамены
  в адрес, только интересы/город/язык/форму/бюджет).
- IP-адрес — не хранится (настройка PostHog).
- Запись сессий (session replay) — не включаем вообще, даже опционально.
- Постоянный идентификатор человека между визитами (никакого cookie,
  никакого localStorage под аналитику — `persistence: "memory"`).
- Текст поискового запроса по каталогу.

## Сверка с политикой конфиденциальности

Текст `privacy.sections.analytics` (оба словаря) уже обещает ровно то,
что выше: без cookies, без сохранения в браузере, без записи полей ввода,
без session recording, IP не хранится. Ни одно событие из этого плана не
требует РАСШИРЯТЬ обещание — `university_slug`/`programme_slug` в
свойствах `calculator_result_shown` не личные данные (это факт о
программе, не о человеке), под «содержимым введённых полей» не подпадает.
Если при реальной интеграции понадобится событие, которое сюда не
укладывается, — сначала менять текст политики, потом код (правило из
`docs/PRIVACY-CHECKLIST.md`: аналитика подключается только после того,
как политика уже это описывает).
