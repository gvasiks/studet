# Снимки подтверждённых фактов

План 2026-09-21, неделя 1, пункт 06: самое дорогое в проекте — не код (он
и так в git), а часы владельца, потраченные на подтверждение формул, сроков,
типов отбора и направлений через Supabase Studio. На бесплатном тарифе
Supabase ежедневных резервных копий нет.

`verified-facts.json` — снимок всех записей с `verified_at is not null`
(формулы, сроки подачи, типы отбора, направления программ) на момент
последнего запуска `.github/workflows/backup.yml` (понедельник, 03:00 UTC).
Обновляется автоматически: `pipeline/src/backup_verified.py`, коммитится
самим workflow, если содержимое изменилось.

**Зачем коммитить, а не просто дампить в артефакт.** Артефакты прогонов
GitHub Actions живут ограниченный срок и не диффятся построчно. Здесь —
обычный файл в git: история изменений видна в `git log -- docs/backups/`,
случайное затирание подтверждения видно в PR-диффе, а восстановить 72
формулы можно **без единого запроса к базе**, если база вообще пропала.

**Чего здесь нет.** Черновики (не подтверждённые записи), сам каталог
программ, данные о выпускниках, ключи, пароли. Полный дамп всей схемы
`public` (включая черновики) уходит в артефакт прогона того же workflow
(`pg_dump`, нужен секрет `SUPABASE_DB_URL`), не в этот файл и не в git:
он больше, содержит то, что ещё не проверено человеком, и незачем хранить
его версии одну за другой.

## Ключи в JSON

Записи адресуются не по UUID (они не переживают пересоздание базы —
seed-скрипты генерируют новые id при каждом запуске), а по устойчивым
слагам: `university_slug` + `programme_slug`. Снимок можно прочитать и
сверить глазами, не разворачивая базу.

## Как восстановить

Скрипт `pipeline/src/restore_verified.py` (без `--apply` — сухой прогон):
по каждой записи находит программу по `(university_slug, programme_slug)` и
пишет факт с протоколом источника и `verified_at` из снимка.

`verified_by` в снимке с 2026-10-25 нет (решение владельца: репозиторий
публичный). После восстановления на пустую базу это поле пустое; кто и
почему подтвердил, видно в скриптах `pipeline/src/confirm_*.py` и в
`docs/checks/`. Старые версии файла в истории git поле ещё содержат.

Копия, которую ни разу не разворачивали, копией не является. **Полный дамп**
с 2026-11-18 разворачивается автоматически в каждом прогоне `backup.yml` (шаг
«Пробное восстановление копии»): чистый Postgres, `pg_restore --exit-on-error`,
сверка числа строк каждой таблицы и числа политик RLS с живой базой. Красный
прогон значит, что копия не разворачивается или неполная. **Раз в год вручную**
остаётся то, чего автоматическая проверка не видит: развернуть этот снимок
через `restore_verified.py` на пустой проект и убедиться, что сайт работает на
восстановленной базе.

## Полный дамп

С 2026-11-16 артефакт `studet-db-dump-<номер прогона>` содержит файл
`studet-public-schema.dump.gpg` — дамп, зашифрованный парольной фразой из секрета
`BACKUP_PASSPHRASE` (репозиторий публичный, артефакт может скачать любой вошедший
пользователь GitHub; `docs/checks/SECURITY-2026-11-16.md`, находка 1). Фраза
хранится ещё и в менеджере паролей владельца: без неё дамп не развернуть, GitHub
показать значение секрета не может.

Скачать артефакт со страницы прогона (Actions → Backup → прогон → Artifacts),
распаковать zip и расшифровать (`gpg` есть в Git for Windows и в любом Linux;
фразу gpg спросит сам):

```
gpg --output studet-public-schema.dump --decrypt studet-public-schema.dump.gpg
pg_restore --list studet-public-schema.dump    # проверить, что внутри
```

Развернуть на чистый проект: `pg_restore --no-owner --no-privileges --dbname "<строка
подключения нового проекта>" studet-public-schema.dump`.
